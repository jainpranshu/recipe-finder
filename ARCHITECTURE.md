# Architecture

Two packages, two responsibilities:

```
recipe-ui-kit/    → "how things look" — dumb, presentational web components
recipe-finder/    → "how things behave" — routing, data fetching, state, business logic
```

Nothing in `recipe-ui-kit` knows what a "favorite" or a "meal plan" is. It only knows how to render a card, a badge, a dialog, and a day cell, and how to emit an event when the user interacts with one. All the actual meaning — what happens when you click the heart icon — lives in `recipe-finder`. That separation is the whole point of building this as a component library rather than just a folder of Svelte components: the same `recipe-card` could be dropped into a React or plain-JS app tomorrow with zero changes.

## Package 1 — `recipe-ui-kit` (StencilJS)

```
src/components/
  recipe-card/    <recipe-card>   — image, title, category badge, favorite toggle
  ui-badge/       <ui-badge>      — small colored label (category, difficulty)
  ui-dialog/      <ui-dialog>     — generic modal shell with a <slot>, Esc-to-close, focus trap
  day-slot/       <day-slot>      — one cell of the weekly planner (empty / assigned states)
```

Each component folder has the same shape:
- `*.tsx` — the component: `@Prop()` for data coming in, `@Event()` for things it needs to tell its parent, `render()` for the markup.
- `*.css` — scoped styles (the components use `shadow: true`, so these styles can never leak out or be overridden accidentally).
- `readme.md` — auto-generated by Stencil from the `@Prop`/`@Event` JSDoc comments on every build. Don't hand-edit these.

**Why events instead of the component managing its own state?** `recipe-card` doesn't track whether it's favorited internally — it just renders whatever `favorited` prop it's given, and emits `favoriteToggle` when clicked. The app owns the actual favorites list and decides what "toggling" means. This is what the assignment calls "presentation-only" components, and it's what makes the library reusable outside this one app.

`stencil.config.ts` is worth a look: `customElementsExportBehavior: 'auto-define-custom-elements'` means that just *importing* a component (`import '.../recipe-card'`) registers the custom element — no manual `customElements.define()` calls needed on the consumer side.

## Package 2 — `recipe-finder` (SvelteKit)

```
src/lib/
  types.ts                      Recipe / RecipeSummary / Ingredient shapes used everywhere
  api/mealdb.ts                 all TheMealDB HTTP calls, isolated in one place
  stores/
    favorites.svelte.ts         $state-backed store, persisted to localStorage
    mealPlan.svelte.ts          same pattern, keyed by day of week
    userRecipes.svelte.ts       same pattern, full CRUD (create/update/remove)
  validation/recipe.ts          pure function: form values → validation errors
  components/
    RecipeCard.svelte           wraps <recipe-card>, wires it to favoritesStore + routing
    RecipePicker.svelte         wraps <ui-dialog>, lets you pick a recipe for a planner day
    ConfirmDialog.svelte        wraps <ui-dialog>, generic yes/no confirmation
    RecipeForm.svelte           the add/edit recipe form (plain HTML — no design-system dependency)
    FavoriteButton.svelte       standalone heart button used on the recipe detail page
    Header.svelte               top nav

src/routes/
  +layout.svelte                 renders <Header/> + page content on every route
  +page.svelte / +page.ts        "/" — discovery: search, category filter, or random recipes
  recipes/[id]/                  recipe detail — fetches from API, or reads local store if id starts with "user-"
  recipes/new/                   create form
  recipes/[id]/edit/             edit form — blocked (403) if the id isn't a "user-" recipe
  favorites/                     lists favoritesStore.all
  my-recipes/                    lists userRecipesStore.all
  planner/                       7 <day-slot> elements + <RecipePicker>
```

### How a request actually flows: the discovery page

1. `routes/+page.ts` `load()` runs (server-side on first load, client-side on navigation). It reads `?q=` / `?category=` from the URL and calls the right function from `lib/api/mealdb.ts`.
2. `mealdb.ts` hits TheMealDB, and maps their raw shape (`strMeal`, `strMealThumb`, `strIngredient1..20`, …) into this app's own `Recipe`/`RecipeSummary` types — so nothing outside this one file needs to know TheMealDB's field-naming quirks.
3. `+page.svelte` renders the results as a grid of `<RecipeCard>` — a Svelte wrapper around the Stencil `<recipe-card>` element.
4. Typing in the search box updates the URL (debounced), which re-triggers `load()`. This is why search state survives a page refresh or a shared link — it's just a URL, not component state.

### How the two packages talk to each other

This is the part the assignment specifically grades ("Integration Requirement"), so it's worth being explicit:

- **Props in:** Svelte passes plain values as element attributes — `<recipe-card recipe-id={recipe.id} favorited={favorited} ...>`. Stencil's `@Prop()` picks these up.
- **Events out:** Stencil emits with `@Event() cardSelect: EventEmitter<string>`. Svelte listens with `oncardSelect={...}` (Svelte 5's event-attribute syntax — no `on:` directive needed for DOM/custom events).
- **Slots:** `<ui-dialog>` renders a `<slot>` internally; `ConfirmDialog.svelte` and `RecipePicker.svelte` put their own markup (a message, a list of recipes) *inside* the `<ui-dialog>` tag, and Stencil projects it into that slot — same mental model as `{@render children()}` in Svelte, just the web-platform version of it.

### State management

There's no global store framework (no Redux/Zustand-equivalent) — three small, independent stores, each following the same shape:

```ts
let data = $state<T>(loadFromLocalStorage());
export const someStore = {
  get all() { return data; },
  mutate(...) { /* update data */; persist(data); }
};
```

Svelte 5's `$state` rune makes a plain object/array reactive; any component that reads `someStore.all` re-renders when it changes, with no subscribe/unsubscribe boilerplate. Persistence is just "write to `localStorage` after every mutation, read it back on module load" — there's no backend in this project (see the main README's Assumptions section for why).

## If you're presenting this

The one-sentence version: *"A published, framework-agnostic web-component library handles all presentation; the SvelteKit app owns all state and data-fetching, and the two communicate only through props and custom events — so the design system has zero knowledge of what a 'recipe' or a 'meal plan' even is."* That sentence is the answer to almost any architecture question you'll get asked about this project.
